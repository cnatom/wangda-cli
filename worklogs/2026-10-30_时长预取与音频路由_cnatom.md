# 预取课程时长与音频路由

## 状态

已完成（v0.8.0）。两件事：`run` 默认在播放前逐门读取课程页上的「课程总时长」并永久缓存；浏览器启动参数不再申请 macOS 的「正在播放」会话，避免抢占蓝牙耳机。

## 预取时长

- `plan_durations`（config，默认 true）。`wanda run` 在开播前展开链接（专题先 `inspect` 成课程列表），跳过已完成/选修，逐门打开课程页读「课程总时长」。
- 缓存在 `<data-dir>/durations.json`，按 course id 存 `seconds`、`source`、`fetched_at`；**不设过期**——课程时长不会变。`--refresh-durations` 强制重读，`--no-plan-durations` 关掉预取。
- 读不到的课程记 `missing`、不入缓存；ETA 回退到本次 run 的实测均值，不阻塞播放。
- 预取独占 profile（与 `inspect` 同锁），所以队列在跑时不会做第二次；平台只允许同一账号同一时刻开一个课程页，预取只能在开播前串行完成。

ETA 现在的优先级：已记录时长（`时长 / rate`）> 本次 run 实测均值 > 只算当前课程。`basis` 分别是 `measured_durations` / `measured_plus_pace` / `observed_pace` / `current_course_only`。

## 音频路由

现象：iPhone 用着 AirPods，macOS 上刷课（无声音）却把 AirPods 抢过去。

原因不是音量：worker 早就 `v.muted = true` 且 `v.volume = 0`，浏览器还带了 `--mute-audio`。抢设备的是「媒体会话」——Chrome 一旦声明 Now Playing，macOS 会把它当成活跃音源。

改动：启动参数合并 `--disable-features=…,MediaSessionService,HardwareMediaKeyHandling,MediaRouter`，并把原来的 `--disable-features` 从 ANTI_FREEZE 里拆出来集中管理（单条 `--disable-features` 更稳妥）。

## 踩到的坑

预取第一次跑出 `fetched: 0, missing: 4`：线上渲染是 **`课程总时长: 1小时47分钟`**（带冒号，且和「上线时间」在同一行），而 `TOTAL_RE` 只允许空白分隔，`\s*` 匹配不到 `:`。补 `[:：]?` 后 4 门全部读到（107 / 100 / 218 / 193 分钟）。这个正则同时被课程学分窗口使用，所以之前那条路径对带冒号的页面也会失效。

## 证据

- `pytest -q`：149 passed / 2 skipped；`ruff check src tests` 全绿。
- 用例：缓存写入/跳过非法值、ETA 使用已记录时长、未知课程回退实测均值（`measured_plus_pace`）。
- 新参数 smoke：headless 打开 `#/home`，`bodylen 5374`，登录态正常。

## 如何继续

- 音频路由的最终确认要真人听：Mac 播课时确认 AirPods 仍连在 iPhone 上；若仍被抢，剩下的可能原因是 Chrome 音频服务仍持有输出设备，这种只能靠虚拟声卡（BlackHole）把 Chrome 的输出钉到空设备，代价是要装系统级扩展，暂不做。
- 若以后课程时长会变，给 `durations.json` 加 TTL 即可；目前按“永不过期 + `--refresh-durations`”处理。
